# 022 権限の設計

状態: todo / 依存: 020

## 目的
誰が何をできるかを設計する。当面は運営だけが操作するが、複数の主催者に開放したときに API とデータの作り直しが出ないよう、タスク 013（画面と API）の前に、役割・操作・ランキング単位の権限と、その持ち方を決める（`docs/product.md` 利用者と操作）。

## 読むべき資料
- `docs/product.md`（対象、利用者と操作、未決事項）
- `docs/architecture.md`（Web サービスの構成の「ログイン」、データモデル、作り直し・取り消し・履歴）
- `docs/decisions.md`（2026-11-20 タスク 014、2026-11-23 タスク 020）
- `docs/tasks/013-web-ui.md`（作業範囲とメモ）

## 作業範囲
- 役割の一覧: 運営・主催者・閲覧者のほかに要るもの（主催者の手伝い＝共同の管理者など）。閲覧者はログインしない前提を保つか
- 操作ごとの許可の表: ランキングの作成・名前の変更・削除、主催者（雀魂のアカウント）の指定、候補の更新、取り込み、対象外にする・戻す、作り直し、操作ログの閲覧、公開 URL の発行・取り直し、利用者の許可（Discord の ID の許可の一覧）と役割の付け外し。それぞれ誰ができるか
- ランキング単位の権限: 主催者 A が主催者 B のランキングを見たり操作したりできないようにする。ランキングと利用者（Cognito の `sub`）の対応の持ち方（DynamoDB の項目の形）。1つのランキングに複数の管理者を置けるか
- 全体の権限と個別の権限の分け方: Cognito のグループ（`operators` など、全体に効く印）と、DynamoDB のランキングごとの対応の使い分け
- 権限の付け外しの手段と流れ: いまは運営が CLI で SSM の許可の一覧とグループを手で変えている。画面で行うか。主催者の招待（招待リンク、運営の承認など）。取り消したときに、Discord から得たデータを消す流れ（Discord の規約。`docs/local/014-login-notes.md`）
- 付け外しの手段の候補として、Discord サーバーのロールを使うか（`guilds.members.read`。Cognito 経由ではこのスコープの結果を受け取れないので、Bot を置いて Lambda から問い合わせるなどの仕組みが要るか）
- 雀魂への負荷との関係: 主催者ごとの手動の更新の間隔・回数の上限を、役割で変えるか
- API での判断の場所: 権限の判断を1か所（例: `authorize(利用者, 操作, ランキング)`）にまとめる形と、操作ログへの記録（誰の権限で行ったか）
- 当面（運営だけ）の形と、開放したときの形の両方を書き、013 で当面の形をどこまで作るかを決める

## 完了条件

- 013 が前提にする部分（API の判断の場所、DynamoDB の項目）が 013 のメモに申し送られている
- 実装が要るものは、新しいタスクとして起票されている
