# 006 運営アカウントでの牌譜回収ツールの実装

状態: done / 依存: 005、007、011、016、017

## 目的
**前提（2026-11-16）**: 目指す形はセルフサービスの Web サービス（`docs/product.md`）。このツールは、そのサーバー側の部品として使えるように作る。ログインは L2 が前提で、L1 は最終手段。
運営のアカウントで、主催者の友人戦の一覧と中身を取り、ランキングの取り込みに使える牌譜 json を出力するツールを作る。主催者に作業を求めない。

## 作業範囲
- **2026-11-19 の構成に合わせる**: 回収処理は、Web サービスの Lambda で動く部品（ライブラリ）として作る。入出力は、候補の一覧を返す関数と、選んだ uuid の牌譜を取って返す関数。取り込み済みの記録は DynamoDB、牌譜の json は S3 に置く（置くのは呼び出し側。タスク 010・013）。手元から試すための小さな CLI も付けてよい。認証情報は SSM Parameter Store から読む（手元では秘密ファイル）。Lambda から接続できることはタスク 011 で確かめ済み。送る雀魂のバージョンはタスク 016、liqi の定義はタスク 017 の方式に従う（`err=151` のときにバージョンと定義を作り直す。手元の試作は `local/probe/` の `fetch-client-version.js`・`decrypt-pb-lua.js`・`lua-pb-to-json.js`）
- 以下の旧来の項目のうち、ファイルでの選択や手元の記録は、上の形に読み替える
- ~~ログイン方法をユーザーに選んでもらう~~ → L2 を希望。**まず L2 が使えるかを検証する**（`docs/decisions.md` 2026-11-16）。最初の検証では Node からのログインが通らず、調査の続きはタスク 007 に分けた。007 の結果でログイン方法を決めてから、このタスクを再開する
  - 使えたら、PaifuImporter の確認（`npm install`、`env.js` とトークンの取り方）も行う（001 から移した）
  - 使えなければ、L1（最終手段）にするかをユーザーに相談する。L1 だと Web サービスにはできない
- ~~主催者の1回の企画あたりの対局数を確認する~~ → 10〜30局。企画ごとに、遅くとも2回に1回は取りに行く（`docs/decisions.md` 2026-11-16）
- 流れ: 主催者の表示用 ID → `searchAccountByEid` → `fetchAccountInfoExtra`（四麻 `category=1`・三麻 `category=2`、`type=2`）→ 取り込み済みでない対局を**候補として一覧で出す（日時・ルール・参加者）→ 運営が選んだ対局だけ** `fetchGameRecordsDetail` → 既存の `parse()` 相当で牌譜 json に変換して出力
  - 自動では取り込まない。主催者の友人戦には、ランキングの対象でない対局もある。選ぶのは、Web サービスの画面で利用者が行う想定（画面はタスク 008 の結論に従う）。それまでの間の選び方（ファイル指定など）は、実装の計画で決める
- 取り込み済み（と、対象外にした）の uuid を手元に記録し、二度出さない。50件の上限に近づいたら警告する
- 主催者の ID、取り込み済みの記録、ログイン状態のプロファイルはコミットしない（`local/` か gitignore 済みの場所に置く）
- 要求の間隔を空ける（検証では2秒）
- 検証用の試作 `local/probe/probe.js`（gitignore 済み。Playwright の環境の作り方は 001 のメモ）を土台にしてよい。リポジトリに入れるコードには、主催者の ID などを書かない
- 運営は非エンジニアとは限らない前提で、実行手順を短くする（`docs/product.md` の非機能要件との関係を整理する）

## メモ
### 2026-11-16 L2 の検証（途中で中断）
- WebGL 版のログインの流れを調べた。結果は `docs/architecture.md`（WebGL 版の通信）に書いた
- Node だけで `oauth2Auth`（`type=21`、ブラウザが使っているのと同じ `code` / `uid`）を送ると `err=151` で失敗した。ブラウザが Yostar の `quick-login` を呼んだ 1.2 秒後に送っても同じだった
- 検証の後、検証用のアカウントでゲームを開くと、自動ログインされず、メール認証を求められるようになった。原因は未確定（ゲームの `oauth2Auth` を途中で止めた試験か、Node からの失敗3回のどちらか）。具体は `docs/local/006-l2-verification-notes.md`
- ユーザーの判断で、いったん止める。L2 の調査は、後でタスク 007 として続ける（`docs/decisions.md` 2026-11-16）

### 2026-11-19 実装と実地確認
- `src/collector/` に、Lambda から呼ぶ部品と手元の CLI を作った。構成は `docs/architecture.md`「牌譜回収」、使い方は `docs/collector.md`、決定は `docs/decisions.md` 2026-11-19（タスク 006）
- 試作（`local/probe/`）の処理を移した。定義の生成は、手元の Lua・キャッシュのバンドルから試作と同じ定義になることを確かめた。送る `requestConnection` は、記録した要求とバイト単位で一致した
- 集計の側に `fromRecordGame`（`src/ranking/record.ts`）を足した。テストは合成データだけで、45件（`npm test`）
- 実地確認（ユーザーの許可を得た）: 静的ファイル5回、ログイン3回、一覧2回、牌譜2回。主催者の友人戦の候補が出て、10件・50件をそれぞれ1回の要求で取れた。主催者は、表示用 ID が手元に無かったので、記録済みの一覧から内部 ID を使った。具体は `docs/local/006-collector-notes.md`
- 計画からの変更: 主催者を内部 ID でも指定できるようにした。外す見た目の情報に `title`・`avatar_frame` を足した。候補に東風・半荘を出した（`sub_tag`）。まとめる件数は 10 → 50
- 認証情報の取り出し（タスク 009 の `login-observe.js`）は、CLI に組み込んでいない。取り出した秘密ファイルから値を写す（`docs/local/006-collector-notes.md`）
