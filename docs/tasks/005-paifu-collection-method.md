# 005 牌譜の回収方式の検討

状態: done / 依存: 001

## 目的

特に、**主催者以外のアカウントから、主催者の友人戦の牌譜を特定できるか**を調べる。できれば主催者の作業がなくなる。

## メモ
### 前提
- 友人戦の牌譜一覧を取る要求（`fetchGameRecordList` / `V2` / `fetchNextGameRecordList`）には相手を指定する項目がなく、本人の一覧しか取れない
- uuid が分かれば、ログインしている人なら誰でも `fetchGameRecord` / `fetchGameRecordsDetail` で中身を取れる
- 雀魂牌譜屋（amae-koromo）は観戦一覧（`fetchGameLiveList`）から金の間以上の段位戦を集めている、という理解。友人戦は対象外

### 2026-11-16 他人の「最近の対局」から友人戦の uuid が取れた
検証用のアカウントでログインしたゲームの接続に相乗りして、別のアカウントを指定する要求を送った。使ったアカウントと結果の具体は `docs/local/005-verification-notes.md`（ローカル限定）。調査用スクリプトは `local/probe/`（gitignore 済み）にある。

- **`fetchAccountInfoExtra(account_id, category, type)` は、他人の友人戦の記録を uuid つきで返す。** ゲームの画面には出ないが API では返る
  - `category`: 1 = 四麻、2 = 三麻 / `type`: 1 = 段位戦、2 = 友人戦（`category=4` は四麻・三麻とも 0件）
  - 1件ごとに `uuid`、開始・終了時刻、`tag`（1 = 段位戦、2 = 友人戦）、`sub_tag`、全員の順位・点数・ニックネームが入る
  - 友人戦の記録が分かっているアカウントで、返った記録の日時が実際と一致し、返った範囲の中では抜けがないことを確かめた
- **件数の上限は、種類ごとに新しいものから 50件**（段位戦を多く打っているアカウントで、50件ちょうどが返った）
- **2024-08〜09 ごろより前の記録は返らない**。それより前に打った友人戦は返らず、ほかのアカウントでも一番古い記録はこの時期だった。この機能が始まる前の記録が無いのだと思われる（推測）
- `account_id` は内部の ID で、プロフィールに表示される ID（eid）とは別。`searchAccountByEid(eid)` で変換できる。表示用の ID をそのまま渡すと `fetchAccountInfo` などが `err=1006` になる
- ほかに他人を指定できて成功したもの: `fetchAccountInfo`、`fetchAccountStatisticInfo`（種類別の統計。uuid は無い）、`fetchAccountState`（フレンドでなくても、オンラインか・対局中かと、対局中の `playing.game_uuid`）

### 接続の注意（WebGL 版）
- ゲームは `jpgs.mahjongsoul.com/gateway` でログインし、その後 `jpgsbk.mahjongsoul.com/gateway` も張る。最初の接続に `.lq.Route.requestConnection` を送る
- ログイン完了前（`fetchInfo` の応答前）に Lobby の要求を送ると `err=1004` になった

### 2026-11-16 取れた uuid で牌譜の中身も取れた
上の一覧で返った四麻・友人戦の uuid を1件使い、その対局に参加していないアカウントから要求した。
- `fetchGameRecord`（`game_uuid` / `client_version_string`）→ `err=0`。`head` に、ルール（`config.category=1`、`mode.mode=1` = 東風）、`meta.room_id` あり（友人戦）、4人分の `accounts`（ニックネームつき）、開始・終了時刻、`result.players` の点数（`part_point_1`）が入っていた。`data` は 31614 バイト（局ごとの記録）で、`data_url` は空
- `fetchGameRecordsDetail`（`uuid_list`）→ `err=0`。`data` は無いが `head` は同じ内容。集計（`parse()` は `head` だけを使う）にはこちらで足り、複数の uuid をまとめて渡せる
- WebGL 版の `client_version_string` は `WebGL_2022-0.16.280`。PaifuImporter の `web-<version>` 形式とは違う
- → **主催者以外のアカウントだけで、「友人戦の uuid を知る → 中身を取る」の両方ができる**

### 2026-11-16 部屋を立てた人の一覧にも入る
上で中身を取った友人戦は、参加者の1人が部屋を立てたもの。その牌譜の参加者から部屋を立てた人の account_id を拾い、その人の友人戦一覧を取った。
- 牌譜の `head.accounts` には、参加者全員の `account_id` とニックネームが入っている
- 部屋を立てた人の四麻・友人戦一覧（上限の 50件に達していた）に、**同じ対局が入っていた**
- → 部屋を立てた側・参加した側のどちらの一覧にも、その友人戦が入る。主催者の一覧を定期的に取れば、主催者の友人戦を集められる
- 50件が何か月ぶんになるかは、対局のペースしだい。主催者のペースに合わせて取りに行く間隔を決める

### 2026-11-16 回収方式の比較と結論
| 方式 | 主催者の作業 | 運営の作業 | 作り直す量 | 弱点 |
|---|---|---|---|---|
| **A. 運営のアカウントから主催者の一覧を取る**（検証済み） | なし | 定期的に実行 | 小（検証用の `local/probe/probe.js` が土台） | 1種類あたり最新50件まで。取りに行く間隔を空けすぎると取りこぼす。2024-08 ごろより前は取れない |
| B. 主催者のブラウザで通信を読み取る userscript | 牌譜画面を開いて保存し、運営に渡す | 受け取って取り込む | 中（通信の解読を userscript 内で行う） | 主催者の手間が残る。ゲーム側の変更で壊れやすい |
| C. 主催者がゲーム内の共有 URL を手で集める | 1戦ごとにコピーして送る | 受け取って取り込む | なし | 手間が大きい。非常用 |

→ **A を採用する**（`docs/decisions.md` 2026-11-16）。B・C は A が使えなくなったときの代替として残す。

### 2026-11-16 ログイン方法の比較（A の実装で使う）
| | L1. ブラウザでログインし、ゲームの接続に相乗りする | L2. PaifuImporter を直し、Node から直接つなぐ |
|---|---|---|
| ログイン | 運営がブラウザで手でログインする。ログイン状態はプロファイルに残り、検証では毎回自動でログインできた | アクセストークンが要る。取り方を新たに調べる必要がある（WebGL 版のログインの流れは未調査） |
| プロトコルの変更への追従 | 接続・ログイン・`client_version_string` はゲーム自身が行うので、ほぼ不要 | `Route.requestConnection`、2本目の接続（`jpgsbk`）、`client_version_string` の新形式などを自前で合わせ続ける |
| 動作の確かさ | 今回の検証で、回収の流れ全体が動いた | 未検証（ログインから先は試していない） |
| 重さ・環境 | 重い（Chromium と WebGL、起動に数十秒）。WSL では Playwright の非公式ビルド・ライブラリ・日本語フォントが必要だった | 軽い。Node だけで動き、定期実行やサーバーでの実行に向く |
| 副作用 | ゲームが知らない番号の応答を受け取る（検証では問題は起きなかった） | なし |

推奨: **まず L1 で実装する。** 動くことが確認済みで、雀魂側の変更への追従もゲームに任せられる。完全な自動化（ログインを含む）はスコープ外なので、運営が時々手でログインする前提で問題ない。定期実行を無人で回したくなったら L2 を検討する。L1 でログインした状態からトークンを取り出して L2 に渡す組み合わせもありうる。
→ どちらにするかは、ユーザーの判断を待つ。決まったら `docs/decisions.md` に追記する。
