# 029 初めての候補の更新が続けて受け付けられる

状態: done / 依存: 025

## 目的
同じランキングへの候補の更新を短い間に続けて送ると、雀魂アカウントの内部 ID がまだ無い（そのランキングで初めての更新）ときは、どれも受け付けられ、ジョブごとに雀魂へログインする。雀魂に余計な負荷をかけないよう、初めての更新にも間隔の確認を効かせる。

## 読むべき資料
- `src/api/routes.ts` の `refresh`（内部 ID が無いアカウントは `reserveRefresh` を数えない）
- `docs/architecture.md`「API」「雀魂に負荷をかけない運用」

## 作業範囲
- 内部 ID が無いアカウントでも、短い間の二重の受け付けを防ぐ（例: ランキングと表示用 ID で予約する、そのランキングで未完了の更新のジョブがあれば 429 にする）。どの形にするかはこのタスクで決める
- 管理の画面のボタンが押せる間（処理の待ち）に二重に送れないかも確かめる

## 完了条件
- 初めての候補の更新を続けて送っても、雀魂へのログインが1回で済む（自動テストで確かめる）

## メモ
- 2026-11-27: API 側は対応しないと決めた（`docs/decisions.md` 2026-11-27 タスク 029）。完了条件の「ログインが1回で済む」は、画面の二重押しに限って満たした。API に続けて送った場合は、これまでどおり2回ログインする。タスク 023 の作業範囲に見直しを移した
- 画面の二重押し: 候補の更新・取り込み・作り直しのボタンは、押してから API が返るまでの間に押せた（`jobRunning` はジョブが画面に届いてから true になる）。`web/src/RankingPage.tsx` の `runJob` で、始めてから終わるまでボタンを止めるようにした（同じ描画の間の連打は ref で弾く）。ほかの操作（作成、対象外・戻す、名前、ID の指定・外す、公開 URL、削除）は、もともと `busy` で止めていた
- 確認: `npm run dev` の画面で、候補の更新と作り直しの要求を Playwright の `page.route` で横取りして1.5秒遅らせ、ボタンを3回押した（本番には送っていない）。変更前は要求が3回、変更後は1回
- 2026-11-25 タスク 027 の本番での確認中に見つけた。apicheck で同じランキングへの更新を続けて2回送り、2つとも受け付けられて、2回ログインした（操作ログに `refresh` が2行）
