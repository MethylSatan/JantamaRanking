## 2026-11-16
- **牌譜の回収は、運営のアカウントから主催者の友人戦を取る方式にする。主催者に作業を求めない**
  理由: 雀魂のブラウザ版が Unity WebGL 版に置き換わり、主催者のブラウザで動かしていた Tampermonkey の2本が動かなくなった。一方で、他人を指定できる `fetchAccountInfoExtra` が友人戦の記録（uuid つき）を返し、その uuid で `fetchGameRecordsDetail` から中身を取れることを検証した。部屋を立てた人の一覧にも、その部屋の友人戦が入る。主催者の手間がなくなり、作り直す量も小さい（比較はタスク 005）。
- **一覧は種類ごとに最新50件までなので、主催者の対局が50件に達する前に定期的に取りに行く**
  理由: 上限を超えると古い対局から取れなくなる。2024-08 ごろより前の記録も取れない。
- **Tampermonkey の2本は使わない。主催者のブラウザで動かす方式（通信を読み取る userscript、共有 URL を手で集める）は、運営アカウント方式が使えなくなったときの代替として残す**
  理由: 現状では動かず、作り直しても主催者の手間が残る。
- **主催者の友人戦を全部は自動で取り込まない。候補の一覧（日時・ルール・参加者）から、取り込む対局を運営が選ぶ**
  理由: 主催者の友人戦には、ランキングの対象でない対局もある（ユーザーの指摘）。
- **ログイン方法は L2（Node から雀魂に直接つなぐ）を希望する。ただし、実装の前に使えるかを検証し、その結果で決める**
  理由: L2 は軽く、定期実行にも向く。一方、WebGL 版のログインの流れは未調査で、Node から通るかは確かめていない（比較はタスク 005）。
- **取りに行く間隔の目安は、企画ごと。遅くとも2回の企画に1回は取りに行く**
  理由: 主催者の企画は1回あたり10〜30局（ユーザーの回答）。2回分でも一覧の上限の50件にほぼ収まる。
- **L2 の検証はいったん止める。調査はタスク 007 として後で続ける。ログイン方法はその結果で決める**
  理由: Node から同じ認証情報で `oauth2Auth` を送ると `err=151` で失敗し、原因が分かっていない。Node だけで完結させるには、Yostar の API の署名を解析する必要がありそう。また検証の後、検証用のアカウントでメール認証を求められるようになったので、続けて試すのは控える（ユーザーの判断）。
- **目指す形は、牌譜の取り込みと集計対象の選定をセルフサービスで行える Web サービスとする（できれば）。ブラウザでログインしてゲームの接続に相乗りする方式（L1）は、L2 が不可能な場合の最終手段とする**
  理由: ユーザーの方針。利用者が自分で取り込み・選定できるようにしたい。L1 は運営の手元のブラウザが要るので、Web サービスにできない。これにより、005 の「まず L1 で実装する」という推奨は取り下げる。L2 の調査（タスク 007）が最優先の前提条件になる。
- **ログイン方法は L2（Node から雀魂に直接つなぐ）にする**
  理由: タスク 007 で、Node だけでログインから牌譜の中身の取得まで通ることを確かめた。`err=151` の原因は、`requestConnection` の項目6（`"Web"`）が抜けていたこと。保存した `code` / `uid` だけで通り、Yostar の HTTP API を Node から呼ぶ必要はない。これで Web サービスの前提条件（`docs/product.md` 目指す形）を満たす。L1 は使わない
- **雀魂の通信を検証するときは、観察のたびに生の frame を手元に保存する（`local/` 内、権限600）。画面やログには値を出さない**
  理由: 保存しておけば、後から何度でも手元で分析でき、ブラウザを起動し直す回数（不審なクライアントとみなされる可能性）を減らせる（ユーザーの指摘）
- **（暫定）運営アカウントの認証情報（`code` / `uid`、取り直し用に端末 ID も）は、サーバー上の秘密ファイル（リポジトリ外、権限600）に置く**
  理由: Node からのログインに要るのはこの値だけ（タスク 007）。有効期間が分かるまでは暫定とし、計測の後に確定する（タスク 009）。
- **（暫定）認証情報の取り直しは、運営がブラウザで一度ログインして値を取り出す方法にする。Node からのメール認証ログインはしない**
  理由: Yostar の SDK を読むと、メール認証ログインは確認コードの送信（`/yostar/send-code`）の段階で CAPTCHA の結果を要求する。Node で通すには CAPTCHA を回避する必要があり、行わない。ブラウザでのログアウトは手元の保存を消すだけでサーバーの API を呼ばないので、それだけでは値は変わらない見込み（未検証）。
- **運営アカウントのユーザーセンターで、ログイン端末を削除しない**
  理由: Yostar は端末ごとにログインを管理している（`device-list` / `remove-device`）。サーバーで使っている値が無効になる可能性がある（未検証）。

## 2026-11-19（タスク 008）
- **Web サービスは AWS に置き、無料枠に極力収める。作り方は word-flashcard に合わせる**（Terraform は `infra/`、状態は共有バケットの別キー、`ap-northeast-1`、GitHub Actions から OIDC でデプロイ）
  理由: ユーザーの方針。同じアカウントですでに静的配信を動かしていて、手順と費用の見通しがある。
- **構成は、CloudFront（定額の無料プラン）→ S3（画面）と Lambda Function URL（API）。雀魂への接続は Lambda から L2 で行う。データは DynamoDB、牌譜の生 json は S3、定期取得は EventBridge Scheduler**
  理由: 利用は少なく間欠的なので、常駐するサーバーは要らない。どれも無料枠か、1円未満の従量に収まる見込み。1回の取得は数十秒で、Lambda の上限（15分）に収まる。Lambda Function URL を CloudFront の配信元にできるか（定額プランの条件を含む）は未確認で、タスク 010 で確かめる。だめなら API Gateway の HTTP API にする（12か月を過ぎると従量。少量なら1円未満）。
- **Route 53 のゾーン、`*.methylsatan.com` の証明書、GitHub の OIDC プロバイダーは word-flashcard のものを参照する（作らない）**
  理由: ゾーンと OIDC プロバイダーはアカウントに1つ。証明書はワイルドカードなので使い回せる。
- **運営アカウントの認証情報は、SSM Parameter Store の SecureString（標準）に置く**（2026-11-16 の「サーバー上の秘密ファイル」を具体化）
  理由: 無料で暗号化でき、Lambda から読める。Secrets Manager は1つ月 $0.40 かかる。取り直しの方法は引き続きタスク 009 で決める。
- **集計はサービスの中で行い、ランキングは Web ページで見せる。スプレッドシートと GAS はやめる。必要なら CSV でダウンロードできるようにする**
  理由: サーバーからスプレッドシートに書くには Google の認証（サービスアカウントとシートの共有）が加わり、見せ方もシートの制約を受ける（ユーザーの判断: シートが厳しいか、より良い画面が作れるなら画面で）。集計のルールは今のシートから移すので、タスク 003 が前提になる。タスク 002 はこれで決着とする。
- **取り込み・選定の操作は、当面は運営だけ。認証は Cognito のユーザープールに運営1人を登録し、自己登録は無効にする**
  理由: 段階的に進める。ユーザーは、認証が解決できれば複数の主催者に開放したい。その段階のログイン方法（X ログインが第一候補）は、料金と、Cognito とのつなぎ方を調べてから決める（タスク 014）。Cognito は X に対応していない。
- **ランキングの閲覧にはログインを求めない。推測されない URL で公開し、noindex を付ける**
  理由: 閲覧者はメンバー限定の友人戦の参加者で、アカウントを作らせたくない。検索に載せないことで、範囲を実質的に絞る。
- **雀魂への要求の運用: 1回の実行につきログインは1回、要求の間隔は1秒以上、1回で取る牌譜の数に上限、同時に実行しない（DynamoDB の条件付き書き込みでロック）、手動の更新は間隔を制限、定期取得は1日1回程度**
  理由: 雀魂のサーバーに負荷をかけない（非機能要件）。規約面の整理は `docs/local/008-terms-notes.md`。
- **Lambda から雀魂に接続できるか（AWS の IP から弾かれないか、運営がブラウザで遊んでいるときに追い出し合わないか）を、基盤より先に確かめる（タスク 011）**
  理由: 構成の前提が崩れるリスクで、確かめる費用は小さい。

## 2026-11-19（タスク 003）
- **旧方式の GAS は、参照用の写しとして `gas/` に置く。clasp では管理しない。スプレッドシートと Drive フォルダの ID は伏せる**
  理由: Web サービスに移って廃止する予定で、今後は更新しない。集計のルールを移すための参照ができれば足りる。ID は公開リポジトリに載せない（元の値は `docs/local/`）。
- **旧スプレッドシートは、移行が済むまで変更しない。読むときは xlsx で書き出して手元で読む**
  理由: ユーザーの指示。今も使われている集計の結果で、移植の答え合わせにも使う。
- **旧集計のルールは、シートの式・GAS・牌譜 json の3つを突き合わせて文書にした（`docs/architecture.md`「旧集計」）**
  理由: pt は GAS ではなく雀魂の計算した値（`total_point`）で、順位は pt の大きい順だと分かった。シートの全対局と、サンプルの牌譜で一致を確かめた。
- **スプレッドシートをやめる決定（タスク 008）の根拠を改める: 旧方式を採った理由3つを、Web サービスで満たせることを確かめた**
  理由: タスク 008 では「サーバーからシートに書くと Google の認証が加わる」ことだけを根拠にしており、比較をしていなかった（ユーザーの指摘）。旧方式を採った理由は、(1) Drive に全牌譜を残せば全部作り直せる、(2) 取り込みの誤りは行を消すだけで戻せ、編集履歴も残る、(3) 見る人がシートで自由に絞り込み・並べ替えできる、の3つ。(1) は S3 のバージョニングと作り直しの機能で、(2) は対象外にする操作・操作ログ・DynamoDB のポイントインタイムリカバリで、上回れる。(3) はシートほどの自由度は出せないが、よく使う並べ替え・絞り込みを画面に用意し、それ以上は要望を受けて足すことで、ユーザーが了承した。要件は `docs/product.md` の非機能要件に書いた。
- **CSV などでの書き出しは用意しない**（タスク 008 の「必要なら CSV でダウンロード」を取りやめる）
  理由: ユーザーの判断。
