## 2026-11-16
- **牌譜の回収は、運営のアカウントから主催者の友人戦を取る方式にする。主催者に作業を求めない**
  理由: 雀魂のブラウザ版が Unity WebGL 版に置き換わり、主催者のブラウザで動かしていた Tampermonkey の2本が動かなくなった。一方で、他人を指定できる `fetchAccountInfoExtra` が友人戦の記録（uuid つき）を返し、その uuid で `fetchGameRecordsDetail` から中身を取れることを検証した。部屋を立てた人の一覧にも、その部屋の友人戦が入る。主催者の手間がなくなり、作り直す量も小さい（比較はタスク 005）。
- **一覧は種類ごとに最新50件までなので、主催者の対局が50件に達する前に定期的に取りに行く**
  理由: 上限を超えると古い対局から取れなくなる。2024-08 ごろより前の記録も取れない。
- **Tampermonkey の2本は使わない。主催者のブラウザで動かす方式（通信を読み取る userscript、共有 URL を手で集める）は、運営アカウント方式が使えなくなったときの代替として残す**
  理由: 現状では動かず、作り直しても主催者の手間が残る。
- **主催者の友人戦を全部は自動で取り込まない。候補の一覧（日時・ルール・参加者）から、取り込む対局を運営が選ぶ**
  理由: 主催者の友人戦には、ランキングの対象でない対局もある（ユーザーの指摘）。
- **ログイン方法は L2（Node から雀魂に直接つなぐ）を希望する。ただし、実装の前に使えるかを検証し、その結果で決める**
  理由: L2 は軽く、定期実行にも向く。一方、WebGL 版のログインの流れは未調査で、Node から通るかは確かめていない（比較はタスク 005）。
- **取りに行く間隔の目安は、企画ごと。遅くとも2回の企画に1回は取りに行く**
  理由: 主催者の企画は1回あたり10〜30局（ユーザーの回答）。2回分でも一覧の上限の50件にほぼ収まる。
- **L2 の検証はいったん止める。調査はタスク 007 として後で続ける。ログイン方法はその結果で決める**
  理由: Node から同じ認証情報で `oauth2Auth` を送ると `err=151` で失敗し、原因が分かっていない。Node だけで完結させるには、Yostar の API の署名を解析する必要がありそう。また検証の後、検証用のアカウントでメール認証を求められるようになったので、続けて試すのは控える（ユーザーの判断）。
- **目指す形は、牌譜の取り込みと集計対象の選定をセルフサービスで行える Web サービスとする（できれば）。ブラウザでログインしてゲームの接続に相乗りする方式（L1）は、L2 が不可能な場合の最終手段とする**
  理由: ユーザーの方針。利用者が自分で取り込み・選定できるようにしたい。L1 は運営の手元のブラウザが要るので、Web サービスにできない。これにより、005 の「まず L1 で実装する」という推奨は取り下げる。L2 の調査（タスク 007）が最優先の前提条件になる。
- **ログイン方法は L2（Node から雀魂に直接つなぐ）にする**
  理由: タスク 007 で、Node だけでログインから牌譜の中身の取得まで通ることを確かめた。`err=151` の原因は、`requestConnection` の項目6（`"Web"`）が抜けていたこと。保存した `code` / `uid` だけで通り、Yostar の HTTP API を Node から呼ぶ必要はない。これで Web サービスの前提条件（`docs/product.md` 目指す形）を満たす。L1 は使わない
- **雀魂の通信を検証するときは、観察のたびに生の frame を手元に保存する（`local/` 内、権限600）。画面やログには値を出さない**
  理由: 保存しておけば、後から何度でも手元で分析でき、ブラウザを起動し直す回数（不審なクライアントとみなされる可能性）を減らせる（ユーザーの指摘）
- **（暫定）運営アカウントの認証情報（`code` / `uid`、取り直し用に端末 ID も）は、サーバー上の秘密ファイル（リポジトリ外、権限600）に置く**
  理由: Node からのログインに要るのはこの値だけ（タスク 007）。有効期間が分かるまでは暫定とし、計測の後に確定する（タスク 009）。
- **（暫定）認証情報の取り直しは、運営がブラウザで一度ログインして値を取り出す方法にする。Node からのメール認証ログインはしない**
  理由: Yostar の SDK を読むと、メール認証ログインは確認コードの送信（`/yostar/send-code`）の段階で CAPTCHA の結果を要求する。Node で通すには CAPTCHA を回避する必要があり、行わない。ブラウザでのログアウトは手元の保存を消すだけでサーバーの API を呼ばないので、それだけでは値は変わらない見込み（未検証）。
- **運営アカウントのユーザーセンターで、ログイン端末を削除しない**
  理由: Yostar は端末ごとにログインを管理している（`device-list` / `remove-device`）。サーバーで使っている値が無効になる可能性がある（未検証）。

- **（上の2項目を改める）`err=151` の原因は、認証情報ではなく、こちらが送る版（`client_version_string`）が古かったこと。認証情報は取得から3.8日後も有効だった**
  理由: ブラウザで自動ログインさせると、ゲームは同じ `code` / `uid` で通り、版は `0.16.287` を送っていた（こちらの固定値は `0.16.280`）。版だけを直して手元から送ると、`oauth2Login` まで通った。ゲームの更新で古い版が拒否されたとみられる。Lambda の失敗も同じ原因だった見込みが高い。

## 2026-11-19（タスク 016）

- **牌譜回収は `src/collector/`（TypeScript）に、Lambda から呼ぶ部品として作る。状態（雀魂のバージョン・定義の置き場所、認証情報、定義の鍵、通知先）は呼び出し側から渡す。手元で試すための CLI を付ける**

  理由: ユーザーの判断。head には参加者の内部 ID が入り、作り直しのときに名前ではなく ID でまとめられる。見た目の情報は集計にも表示にも使わない。外すと1件あたり json で約2.6KB → 約1.2KB、gzip で約0.9KB → 約0.55KB（実地で取った60件の平均。外す前の値は1件で測ったもの）。年500局でも1MB 前後で、費用の差はほぼないので、外す理由は使わないデータを持たないこと。段位（`level`・`level3`）は画面に出せるので残す。`title`・`avatar_frame` は計画の時点では挙げていなかったが、同じく見た目の情報なので外した。mjlog は旧方式の牌譜を読むため（`fromMjlog`）だけに残す。

  理由: 主催者の表示用 ID が手元に無く、記録済みの一覧の参加者から内部 ID が分かった。内部 ID なら `searchAccountByEid` が要らず、要求が1回減る。データモデル（`docs/architecture.md`）でも主催者の内部 ID を持つ。
- **候補の東風・半荘は、一覧の `sub_tag` から出す**
  理由: 実地で取った60件で、`sub_tag` が牌譜の `config.mode.mode` と全件一致した。牌譜の中身を取らずに、候補の段階で表示できる。意味を確かめていない値（4）は、名前を付けずに数のまま出す。
